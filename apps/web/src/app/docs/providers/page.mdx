## Connection lifecycle

Every provider guide documents the same operational questions: where to obtain the credential, permissions/credential type, encrypted storage, model discovery, quota/rate-limit evidence, known limitations, and disconnection.

The general lifecycle is:

1. Choose a provider from the gateway catalog.
2. Enter its credential and provider-specific connection fields.
3. Test the credential and discover/normalize available models.
4. Save only after validation succeeds.
5. Add discovered models to Routes.
6. Re-test when credentials/models change or health needs refresh.
7. Remove Route references before disconnecting the provider.

Saved credentials are encrypted by the gateway and stored outside the browser-readable schema. The browser receives only provider identity, safe connection metadata, health, and discovered model metadata.

## Metadata and routing evidence

Pricing, quota, context limits, output limits, and capabilities are used only when SwitchRoute has evidence for them. Missing information remains `unknown`.

- Unknown price is never treated as free.
- Unknown quota is never treated as unlimited.
- Unknown latency does not automatically win Fastest.
- A `free_capable` label does not prove currently available free capacity.

Provider-specific rate-limit headers and catalog data are normalized with provenance/confidence where possible. See [Routes](/docs/routes) for strategy semantics.
